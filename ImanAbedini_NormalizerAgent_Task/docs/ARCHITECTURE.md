# مستند معماری سامانه‌ی نرمال‌ساز فانوس (`Fanos Normalizer Agent`)

این مستند تشریح‌کننده‌ی معماری فنی، جریان داده‌ها و تصمیم‌های طراحی مؤلفهٔ نرمال‌ساز (`Normalizer Agent` یا `LLM Normal`) در پایپ‌لاین هوش داده‌ای بازار کار ایران است.

---

## ۱. هدف و فلسفهٔ طراحی

عامل نرمال‌ساز وظیفه دارد داده‌های خام استخراج‌شده از آگهی‌های استخدامی وب‌سایت‌های ایرانی (نظیر جابینجا، کاربوم، ایران‌تلنت، جاب‌ویژن و کوئرا) را دریافت کرده و به یک مدل استاندارد، معتبر و یکپارچه تبدیل کند.

اصول بنیادی طراحی سیستم عبارت‌اند از:
1. **اولویت قطعی بودن (`Deterministic-First`):** تبدیل کاراکترها، اعداد، تاریخ‌ها، مبالغ حقوق و عبارات رایج پیش از هرگونه فراخوانی مدل زبانی (`LLM`) و بدون تحمیل هزینه انجام می‌شود. مدل زبانی فقط به عنوان لایهٔ پشتیبان برای مقادیر مبهم یا ترکیبی به کار گرفته می‌شود.
2. **عدم حدس‌زدن (`Never Guess`):** اگر مقداری با اطمینان کافی نگاشت نشود، سیستم مقدار استاندارد اختراع نمی‌کند؛ بلکه فیلد را `null` گذاشته و آن را همراه با دلایل مشخص به صف بازبینی انسانی (`needs_review`) ارسال می‌کند.
3. **استقلال از تأمین‌کننده (`Provider-Agnostic`):** تغییر مدل زبانی یا سرویس‌دهنده تنها با ویرایش فایل `config/llm.yaml` انجام می‌پذیرد و هیچ نام تأمین‌کننده‌ای خارج از لایه‌ی آداپتورها نفوذ نکرده است.
4. **تغییرناپذیری اصالت رکورد (`Provenance Immutability`):** فیلدهای اصالت شامل `document_id`، `text`، `content_hash`، `collector` و تاریخ‌ها هرگز دستخوش تغییر یا نرمال‌سازی نمی‌شوند.
5. **قابلیت حسابرسی کامل (`Full Auditability`):** برای تک‌تک فیلدها، روش نرمال‌سازی (`rule`، `lookup`، `llm`، `cache`)، مدل و میزان اطمینان در آرایهٔ `audit` ثبت می‌گردد.

## ۲. جریان پردازش رکورد (`Pipeline Flow`)

جریان پردازش داده‌ها در هر چرخه شامل ۶ مرحلهٔ اصلی است:

```
[ورودی خام: JobAdRaw]
         │
         ▼
[مرحله ۱: یکپارچه‌سازی متنی و حذف الگوهای پیش‌پاافتاده (unify / placeholders / parens)]
         │
         ▼
[مرحله ۲: اعمال قواعد قطعی ریاضی، تاریخ و واژگان (rules / vocabulary lookup)]
         │
    ┌────┴────────────────────────┐
[تمام فیلدها حل شدند؟]            [خیر، فیلدهای نامشخص باقی مانده]
    │ بلی                         │
    │                             ▼
    │                   [مرحله ۳: بررسی حافظه پنهان SQLite]
    │                             │
    │                        ┌────┴────────────────┐
    │                   [Cache Hit]           [Cache Miss]
    │                        │                     │
    │                        │                     ▼
    │                        │          [مرحله ۴: فراخوانی تجمیعی LLM]
    │                        │          - ارسال یک درخواست برای کل رکورد
    │                        │          - مقاومت در برابر خطا (Fallback Router)
    │                        │          - حلقهٔ تعمیر JSON در صورت خرابی خروجی
    │                        │                     │
    │                        │                     ▼
    │                        │          [مرحله ۵: اعتبارسنجی قطعی خروجی مدل]
    │                        └──────────────┬──────┘
    │                                       │
    └───────────────────┬───────────────────┘
                        ▼
    [مرحله ۶: تجمیع پاکت خروجی (Assembly / JobAd Envelope)]
                        │
                        ▼
     [خروجی استاندارد: NormalizeResult (JobAd + Audit + Review)]
```

## ۳. لایه‌ها و پکیج‌های سامانه

ساختار ماژولار پروژه در پوشهٔ `src/normalizer_agent` به بخش‌های زیر تفکیک شده است:

* `schemas/`: مدل‌های «`Pydantic v2`» شامل `JobAdRaw`، `JobAd`، ساختار پاکت `NormalizeResult` و انواع برشمرده (`Enums`).
* `text/`: توابع پردازش رشته و نویسه‌ها شامل یکپارچه‌سازی حروف عربی به فارسی، تبدیل ارقام به «`ASCII`»، تفکیک یادداشت‌های داخل پرانتز و شکستن رشته‌های ترکیبی.
* `rules/`: قواعد تبدیل مبالغ ریالی و تومانی، تقویم جلالی به میلادی با الگوریتم چرخهٔ ۳۳ ساله، تبدیل اعداد حروفی فارسی به رقم و بازه‌های سابقه و سن.
* `vocab/`: زیرسیستم واژگان کنترل‌شده بر پایهٔ فایل‌های «`CSV`»، تولید چک‌سام امنیتی «`SHA-256`» و موتور جستجوی شباهت «`Trigram Jaccard`».
* `llm/`: پورت‌ها و آداپتورهای مدل‌های زبانی، مسیریاب هوشمند پشتیبان (`FallbackRouter`)، قطع‌کنندهٔ مدار (`CircuitBreaker`) و محدودکنندهٔ نرخ (`RateLimiter`).
* `cache/`: پایگاه دادهٔ محلی «`SQLite`» با قفل‌گذاری بهینه جهت پیشگیری از فراخوانی‌های تکراری مدل‌ها.
* `validate/`: اعتبارسنجی‌های پس از مدل زبانی (بررسی ساختار نگارشی، تطابق با واژگان مجاز و بررسی منطق ریاضی).
* `pipeline/`: جمع‌آوری فیلدها (`Collector`)، حل‌کنندهٔ قطعی (`DeterministicResolver`)، صحنهٔ مدل زبانی (`LLMStage`) و اسمبلر رکورد نهایی (`_Assembly`).
* `interface/`: واسط‌های تعاملی شامل رابط خط فرمان (`CLI`)، هماهنگ‌کننده (`CoordinatorAdapter`) و وب‌سرویس (`FastAPI`).

---

## ۴. امنیت و مدیریت خطاها

1. **کلیدهای محرمانه:** کلیهٔ کلیدهای ارتباطی از طریق متغیرهای محیطی خوانده می‌شوند و هرگز در فایل‌های کانفیگ نوشته نمی‌شوند.
2. **عدم ثبت متن در لاگ‌ها:** متن کامل آگهی‌ها و کلیدهای اعتبارسنجی در لاگ‌های با سطح «`INFO`» ماسک یا حذف می‌شوند.
3. **پایداری سیستم:** بروز خطای اعتبارسنجی یا نقص ساختار در یک رکورد هرگز اجرای کل بسته (`batch`) را متوقف نکرده و وضعیت رکورد معیوب به صورت «`rejected`» در پاکت خروجی مستند می‌گردد.
